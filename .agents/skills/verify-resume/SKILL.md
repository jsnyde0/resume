# verify-resume — agentic end-to-end for the resume site

Generated by `/verify scaffold`. This skill is **this project's glue around a shared browser engine**, not a copy of one. It knows how to start this site, which routes matter, which selectors are real, and what proves a feature works. Driving a browser is the shared `browser-automation` skill's job, and this skill calls it by path.

## What this catches that the existing checks do not

Checks already exist here, and they are worth running first. `.claude/verification.md` is the canonical list — do not keep a competing one in this file. As of 2026-09-05 it names:

- `npm run build` — proves the routes compile.
- `npm run test:projects` — reads built HTML off disk and pins the `/projects/` content.
- Cloudflare Pages preview — each route checked for route-specific content, not just HTTP 200.

None of them can see **client-side behaviour**. The repo explorer on `/resume/` and the orbit graph on `/factory/` are inline vanilla JS that rewrite the DOM in place on click (the explorer also rewrites the `#path` hash and, at <=860px, moves the open file inline under its row). To a static-HTML reader they are invisible: the markup is identical whether the click handlers work or were never wired at all.

**This skill is not the only thing here that pays for a browser — it is the only thing that clicks.** A static-HTML or computed-style check measures a page standing still; it would pass on a page whose every handler is dead. The distinction worth holding is act-then-observe, not browser-versus-no-browser.

## The repo interview

Answered from the codebase on 2026-09-05. Recorded so the next reader can check them rather than re-derive them.

- **Surface** — a static-generated Astro site. No SSR adapter and no framework islands (`astro.config.mjs` has no `output` or adapter; dependencies are `astro` and `@astrojs/sitemap` only). Interactivity is plain inline `<script>` tags with no hydration directives.
- **Run** — `npm run dev` (`astro dev`, source, live reload) or `npm run preview` (`astro preview`, serves `dist/`). Both default to port 4321 and take `--port`. This skill uses **preview on port 4329**, after a build: a non-default port so it cannot collide with a dev server you have open, and a build first because `astro preview` will happily serve a stale `dist/`.
- **Drive** — five routes, one file each in `src/pages/`: `/` (index), `/resume/`, `/readme/`, `/projects/`, `/factory/`.
- **Observe** — see the table below. Each observable is route-specific: it would not appear on another route, so a server answering 200 with the homepage for every path fails rather than passes.
- **Isolate** — hermetic once `node_modules` exists. No database, no cache, no external API, no auth session; no `fetch(`, `process.env` or `import.meta.env` anywhere in `src/`. The root `db.sqlite3` belongs to the legacy Django stack, which no Astro source reads. So `scripts/seed` has nothing to do and says so.

**One repo, two apps.** `www.jonatansnyders.com` is still served by the legacy Django stack in this repo (`a_core/`, `templates/`, `node/`); the Astro site is the unfinished migration target. **This skill drives the Astro site only.** Nothing here starts, touches or verifies Django.

## The drive engine

The shared `browser-automation` skill, **wrapped by path, never copied**. `scripts/_common` resolves it by trying, in order: `$VERIFY_RESUME_BROWSER_SKILL`, `$SKILL`, `~/.claude/skills/browser-automation`, `~/code/personal/dotpi/agent/skills/browser-automation`. A candidate counts only if it holds both `nav.js` and an installed `node_modules`.

**Resolution is by trying, on purpose.** `$SKILL` is how the engine documents its *own* invocation, but it is a per-skill variable: when `verify-resume` is the skill being invoked, `$SKILL` points at `verify-resume`, which has no `nav.js`. It is in the list as a courtesy for a caller who exported it deliberately, and the both-files guard is what makes a wrong value fall through instead of being used. Nothing guarantees `$SKILL` is set at all in a spawned child. `scripts/doctor` prints the path that won and refuses to drive when none does.

The last candidate is a `$HOME`-relative path into the dotpi checkout. That is a machine-specific assumption shipped in this repo, and it is the fallback rather than the first choice for exactly that reason — set `VERIFY_RESUME_BROWSER_SKILL` on any machine where it does not hold.

## Running it

```bash
scripts/doctor              # read-only: is this worth driving? (run it first)
scripts/launch              # build, then serve dist/ on 127.0.0.1:4329
scripts/seed                # nothing to seed here; says so and exits 0
scripts/drive file-tree     # expand a folder chain, open a file; 1440x900 two-pane and 390x844 accordion
scripts/drive reading-path  # experience -> achievements in <=3 taps, no scroll; deep links; folder counts
scripts/drive identity [route ...]  # D1 ground, self-hosted heading face, no untokenized hex (default /resume/)
scripts/drive screenshots   # 10 full-page PNGs + 10 computed-style fingerprints
scripts/drive font-gate     # font preload, gate hidden/ready/failed under held/aborted/stalled woff2
scripts/drive home-contacts # / contacts, outfit halo, held/failed font, links: 7 sizes x Chrome + Firefox
scripts/compare A B         # diff two screenshots-* evidence dirs
scripts/cleanup             # stop only what launch started; evidence survives
```

Evidence lands in `.verify-evidence/<feature>-<timestamp>/` at the repo root: screenshots of each step and an `evidence.json` holding every check with its result and the observed state (files discovered, what was expanded and pressed, taps, first-line positions).

**Parallel runs.** Two drivers sharing the automation Chrome at once (for example two worktrees) must use different ports and tab labels: `VERIFY_RESUME_PORT=<port> VERIFY_RESUME_LABEL=<label> scripts/...`. Defaults: port 4329, label `verify-resume`. The `font-gate` drive uses a throwaway browser context and needs no label. `cleanup` never deletes it.

`cleanup` stops the preview server and **only** processes it can prove are that server's descendants — it collects the ancestry before stopping anything and leaves anything else alone, loudly. It deliberately leaves the shared automation Chrome on `:9222` running, because other skills and other agents reuse it; the drives reuse one labelled tab (`VERIFY_RESUME_LABEL`) rather than opening one per run, so nothing accumulates.

## Screenshots drive (before/after baseline)

`scripts/drive screenshots` visits `/`, `/resume/`, `/readme/`, `/projects/`, `/factory/` at 1440px (desktop) and 390px (mobile) and writes to `.verify-evidence/screenshots-<timestamp>/`: `<page>-<viewport>.png` (full page) and `<page>-<viewport>.fingerprint.json` (10 + 10 files, plus `evidence.json`). Page names: `home resume readme projects factory`; viewports: `desktop mobile`.

The fingerprint is one entry per element under `<html>`/`<body>` (script/style/noscript/template skipped), keyed by a structural path (`html>body>div.site-shell>nav.navbar...`: tag, `:n` among same-tag siblings, classes; never ids). Each entry holds computed color, background-color/-image, border width/style/color per side, per-corner border-radius, box-shadow, font-family/size/weight, line-height, letter-spacing, margin/padding per side, row/column gap, opacity. `::before`/`::after` get their own entries when their `content` is not none/normal.

`scripts/compare <baselineDir> <afterDir>` prints per page: PNG byte-equality and the fingerprint diff (changed/added/removed elements and the differing properties). Exit 0 and `COMPARE-RESULT: identical` only when all PNGs are byte-equal and no fingerprint differs. Used as the before/after gate for the resume-soe.1..5 design-system work: capture a baseline on the unchanged tree, change, capture again, compare. A deliberate visual change shows up as diffs; an intended no-op refactor must show none.

**Determinism: what is frozen or excluded** (the run is only useful as a baseline because two runs on one tree compare identical):

- `prefers-reduced-motion: reduce` is emulated, so page JS that checks it (the factory graph does) takes its motionless path.
- A stylesheet injected after load sets `animation: none`, `transition: none`, `scroll-behavior: auto`, `caret-color: transparent` on everything, so no frame is captured mid-transition. The `transition`/`animation` properties are not fingerprinted anyway.
- Capture waits for `networkidle0`, `document.fonts.ready`, then a 600 ms settle, and scrolls to top.
- Fingerprints hold style values only, never text: time-based copy (the footer build year from `new Date().getFullYear()`) cannot enter them. The PNGs do show that text, so a baseline taken in one calendar year and compared in the next will report a PNG diff on every page: re-baseline across a year boundary.
- No generated ids or text in path keys.
- Fingerprint is read BEFORE the full-page screenshot. Puppeteer resizes the viewport to the page height for `fullPage`; reading styles while that is in flight flaked (`.site-shell` auto margins read 0px instead of 16px on `/factory/` mobile, 2 of 5 runs). After the reorder, 6 of 6 consecutive runs were stable.
- Device scale factor pinned to 1; the shared Chrome's viewport and media emulation are cleared at the end of the run.
- Not covered: hover/focus/active states, JS-driven states after clicks (see `scripts/drive file-tree`), other viewport widths, anything below `<body>` text content.

## Home-contacts drive (the F7 composition on `/`)

`scripts/drive home-contacts` measures what the home page is for (bead `resume-soe.18`, contract in `resume-soe.12` D4 + Verification target Signal 1). Evidence: `.verify-evidence/home-contacts-<timestamp>/evidence.json` plus a PNG per engine, size and scenario.

- **Matrix:** 1280x800, 1440x900, 1920x1080, 1024x768, 1280x1024, 390x844, 768x1024, in Chrome (the shared `:9222` Chrome, inside a throwaway browser context, so it never shares a tab with another drive or agent) and Firefox (headless, launched through puppeteer-core's WebDriver BiDi from `$VERIFY_RESUME_FIREFOX`, default `/usr/bin/firefox`). WebKit is printed as `NOT RUN`: puppeteer cannot drive it. `VERIFY_RESUME_ENGINES=chrome` narrows the run.
- **Contacts:** landmarks are fractions of the rendered, mirrored img box (the photo's alpha landmarks, never the box edges); the target glyph's ink comes from a figure-hidden screenshot scanned inside the glyph's Range rect. Pass: landmark 0-4px from the ink, and the clog no more than 4px sunk below the ink top. The branch is read from the page's own media queries (so 1280x1024, aspect 1.25, is measured in the narrow branch).
- **Halo:** ground pixels 2-8px from the shirt must hold zero hue 60-110deg / saturation > 0.25 pixels.
- **Held / failed font:** the woff2 held 2s keeps tagline, name and figure hidden on every frame; aborted, the page settles `fonts-failed` with a contact-free layout and reachable links.
- **Links:** all four inside the viewport and hit at their centre at every size; both internal links clicked for real.
- Red-capable: moving the wide clog 0.06em (`--sy`), dropping `data-font-gate` from the name, and a lime glow on the figure each turned the run red, only at the sizes they affect (resume-soe.18 ship-record).

## Evidence standards

These are the bar for any drive added to this skill. The first one is a family-wide rule with its own home — **the `/verify` skill's own `references/output-not-exit-code.md`** (inside the `/verify` skill, *not* this skill's `references/` directory below), which carries five worked instances of a harness going green while the goal was missed. Read it before arguing that a cheaper check is good enough here.

- **Check what came out, not the exit code.** A drive that exits 0 having discovered zero files and asserted nothing is green and worthless. Every drive prints its population — how many elements it found, which ones, what it observed before and after — so a reader can tell a real run from a vacuous one. `drive-file-tree.mjs` prints the discovered file list for exactly this reason.

  *On precision, the other half of that rule:* a drive asserts against a known expected state rather than emitting findings to be judged, so it has no false-positive rate to sample — its checks are right or the run is red. Precision becomes live here the moment a drive starts *reporting* things rather than asserting them.
- **Exercise the real user path, and prove the target was reachable.** Click the thing a visitor clicks — and first check a visitor could have clicked it. Most files in this tree start inside a collapsed folder, so an earlier version of the drive clicked a hidden node and passed while the entire folder-expand feature could have been dead, leaving a visitor able to open nothing. The drives now pick a *hidden* file on purpose, expand its folder chain the way a visitor does, and press only through `visitorPress` (`scripts/lib.mjs`), which **refuses any target that is off-screen or covered** (viewport plus `elementFromPoint` hit-test) and never scrolls. Presses are real mouse clicks or touchscreen taps at the target's centre. Do not call the page's internal function directly either; that tests the function, not the feature.
- **Capture the action and the resulting state, not just a final screenshot.** A screenshot of the end state cannot distinguish "the click worked" from "it already looked like that". Capture before, act, capture after, and require the difference.
- **Assert every observable the behaviour is supposed to move, and make them agree.** Opening a file moves `aria-current`, panel visibility, the `#path` hash, the path line (two-pane) or the inline placement under its row (accordion), and the drive requires all of them to move *and to name the same path*. Any one alone would pass while the feature was half broken.
- **Discover selectors from the live DOM where the markup is data-generated.** The file tree is built from repo data. A hardcoded path list would rot on the next data change and would fail as though the feature broke.
- **Compare whole identifiers, not fragments.** The path-line check resolves the rendered text back to a full path and compares that. A basename-only check would pass on a wrong directory prefix — and this tree has four basenames that each live in two directories (`mapular.md`, `moonbird.md`, `humainly.md`, `kuleuven.md`), so that is a live weakness, not a theoretical one.
- **Count the checks, never announce a number.** The run prints how many checks it ran, derived from the checks themselves. A hardcoded count is a lie waiting for the next edit, inside the very output whose job is honesty.
- **Route-specific observables only.** Never assert on something the homepage also has; a misrouted server would pass.
- **Verify side effects, not only the visible surface.** No page writes `localStorage`, `sessionStorage` or a cookie. The one non-DOM effect is the `/resume/` explorer's `#path` hash (`history.replaceState`), and the drives read it back. That stops being enough the moment a feature persists anything (a remembered theme, a saved filter, a visited-file list). When one does, asserting the rendered surface is no longer enough: read the stored value back. The skill's own side effect counts too — the evidence directory must exist after `cleanup` has run.
- **A "dry-run" flag must be proven to skip.** No script here takes one today. If one is ever added, a run with the flag has to be shown to leave the thing it names untouched — a dry-run that quietly does the work anyway is worse than having no flag, because it is trusted.

## Maintaining this skill

Whoever invokes this skill and hits friction — `doctor` fails, a selector is dead, a feature is missing from the map — **fixes it inline when it is documentation or map drift**, and otherwise **files the maintenance work then and there**. Do not work around a broken drive silently; a drive that has been quietly bypassed is worse than one that is red, because it still reads as coverage.

The heavier full pass — re-read every feature source, **drive every feature that has a drive; list the rest as documented-not-driven**, then sort what breaks into documentation drift, harness gap, coverage gap, or a real product regression, and report exactly one of clean / changed / blocked — runs on **named triggers only**: filed drift has accumulated, an audit flags it, **the pane-verb / drive-engine surface changes**, or the human asks. **There is no cadence.** Product code is never edited by a maintenance pass.

On this site that phrasing is load-bearing rather than pedantic: four of the five mapped features have no drive, so "drive every mapped feature" would describe a pass nobody can run. The phrase is also fixed wording — every copy `grep -rF` finds, here and across the `/verify` skill, comes back byte-for-byte identical. The grep is the inventory; do not keep a list of the sites here.

**`changed` covers every completed pass that found something**, including the findings this skill is forbidden to fix: a product regression is reported, not patched, and the pass is still `changed`. `clean` means the pass completed and found nothing; `blocked` means it could not complete.
